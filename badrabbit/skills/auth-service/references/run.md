# Running auth

## Horizontal scaling
Auth and every consumer run in N replicas without code changes.
- No state in the process: refresh sessions in PostgreSQL; blocklist, limit and lock counters in Redis; config from env. Any replica serves any request; no sticky sessions.
- One key for all replicas, from a secret or the `auth-keygen` volume; never generated by a replica.
- Concurrent refresh on two replicas is closed by a row lock or a conditional `UPDATE`.
- Migrations by a one-shot `auth-migrate` service, never by each replica at start.
- Periodic cleanup of expired `refresh_sessions` in exactly one instance: a scheduler service or a replica holding a leader lock (`SET key value NX EX ttl`). No cron per replica, no cleanup at start. Redis keys expire by TTL.
- Pool size × processes × replicas < PostgreSQL `max_connections`.
- Consumers scale freely: verification is local crypto; each process caches JWKS.
- Check: `docker compose up -d --scale auth=3` and "login → request → refresh → logout" behaves as with one replica.

## Compose
The whole stack: `cp .env.example .env && nix run .#images && docker compose up -d`. The example below is the Dockerfile variant (`build:`); with Nix images use `image:` from `nix run .#images`, and commands/healthchecks are the package's own entry points (distroless has no `python` or `curl`).

```yaml
x-auth-env: &auth-env
  AUTH_ENV: ${APP_ENV:-dev}
  AUTH_DATABASE_URL: postgresql+asyncpg://auth_svc:${AUTH_DB_PASSWORD}@auth-db:5432/auth
  AUTH_REDIS_URL: redis://auth-redis:6379/0
  AUTH_JWT_PRIVATE_KEY_FILE: /keys/jwt.key
  AUTH_JWT_AUDIENCE: ${AUTH_JWT_AUDIENCE:-app-api}
  AUTH_ACCESS_TTL_MINUTES: ${AUTH_ACCESS_TTL_MINUTES:-15}
  AUTH_REFRESH_TTL_DAYS: ${AUTH_REFRESH_TTL_DAYS:-14}

services:
  auth-db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: auth_svc
      POSTGRES_PASSWORD: ${AUTH_DB_PASSWORD:?see .env.example}
      POSTGRES_DB: auth
    volumes: ["auth-pg:/var/lib/postgresql/data"]
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U auth_svc -d auth"], interval: 5s, retries: 20 }

  auth-redis:   # blocklist and counters: no eviction, AOF on
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes", "--maxmemory-policy", "noeviction"]
    volumes: ["auth-redis:/data"]
    healthcheck: { test: ["CMD", "redis-cli", "ping"], interval: 5s, retries: 20 }

  auth-keygen:  # dev only: creates the key pair if missing; never overwrites
    build: ./src/auth
    command: ["python", "-m", "app.cli.keygen", "--dir", "/keys"]
    volumes: ["auth-keys:/keys"]
    restart: "no"

  auth-migrate:
    build: ./src/auth
    environment: *auth-env
    command: ["alembic", "upgrade", "head"]
    restart: "no"
    depends_on:
      auth-db: { condition: service_healthy }

  auth:
    build: ./src/auth
    environment: *auth-env
    volumes: ["auth-keys:/keys:ro"]
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3)"]
      interval: 10s
      retries: 10
    depends_on:
      auth-keygen: { condition: service_completed_successfully }
      auth-migrate: { condition: service_completed_successfully }
      auth-redis: { condition: service_healthy }

  orders:       # any consumer: public keys only, own DB, NO depends_on on auth
    build: ./src/orders
    environment:
      ORDERS_AUTH_JWKS_URL: http://auth:8000/.well-known/jwks.json
      ORDERS_AUTH_ISSUER: auth
      ORDERS_AUTH_AUDIENCE: ${AUTH_JWT_AUDIENCE:-app-api}

volumes:
  auth-pg:
  auth-redis:
  auth-keys:
```

- Pinned tags; data in named volumes; healthchecks; `depends_on` with conditions.
- Services reach each other by name (`auth:8000`), never `localhost`. Auth is not published: the reverse proxy (Caddy/nginx) sends `/api/auth/*` and `/.well-known/*` to `auth:8000`. A debug DB port only as `127.0.0.1:${AUTH_DB_HOST_PORT:-15433}:5432`.
- Image built with Nix (`nix/auth.nix`): non-root, `/keys` a mounted volume, key file mode `600`. Dockerfile variant: pinned `python:3.13-slim`; manifest and `uv sync --frozen --no-dev` before the code; non-root user (`useradd --uid 10001 app`); `/keys` owned by `app`; exec-form `CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--proxy-headers"]`.
- Never keys or secrets through `ARG`/`ENV`; never `COPY .env`. `.dockerignore` and `.gitignore` list `.env`, `.env.*` (except `.env.example`), `*.key`, `*.pem`, `keys/`, `.venv`.
- `keygen` is idempotent. Deleting the `auth-keys` volume logs everyone out; like `docker compose down -v`, only with the user's explicit confirmation.
- Prod: a separate `docker-compose.prod.yml` with registry `image:` by version, no `auth-keygen`, `AUTH_ENV=prod`, the key through `secrets:` or a platform secret at `/run/secrets/jwt_private_key`. Auth checks at start that the key exists, is readable, and matches the algorithm.

```dotenv
# --- auth ---
AUTH_DB_PASSWORD=change-me-auth-db       # local value; any string works
AUTH_JWT_AUDIENCE=app-api                # product API id, same in auth and consumers
AUTH_ACCESS_TTL_MINUTES=15               # 5–60
AUTH_REFRESH_TTL_DAYS=14                 # 1–90
# The signing key is NOT here: auth-keygen creates it locally, a platform secret in prod
```
