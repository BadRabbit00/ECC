# ECC — полный гайд по командам (для агента и для Архитектора)

ECC установлен через Nix (`home/ai/ecc`). Команды ниже доступны в Claude Code как `/имя`, в Codex как промпты `/ecc-имя`; скиллы вызываются `/имя` (Claude) и `$имя` (Codex); агенты поднимаются через Agent/sub-task по имени. Скрипты ECC запускаются только через `ecc-run`, пути уже прописаны внутри скиллов.

## Проактивное использование (без явной команды пользователя)

Агент обязан сам применять ECC там, где подходит, не дожидаясь слэш-команды:

| Ситуация | Что применить |
|---|---|
| Запрос на новую фичу, крупную правку, неясные требования | `/plan` (агент `planner`), для архитектуры `architect` |
| Любой новый код или багфикс | `/tdd-workflow` + языковой `/rust-test`, `/go-test`, `/react-test`, `python-testing` |
| Код написан или изменён | `/code-review` или языковой `/rust-review`, `/python-review`, `/fastapi-review`, `/react-review`, `/vue-review`, `/go-review`, `/cpp-review`, `/kotlin-review`, `/flutter-review` |
| Код трогает ввод пользователя, auth, секреты, SQL, сеть | агент `security-reviewer`, скилл `security-review`; перед релизом `/security-scan` |
| Сборка или типы упали | `/build-fix`, языковые `/rust-build`, `/go-build`, `/react-build`, `/cpp-build`, `/kotlin-build`, `/gradle-build`, `/flutter-build` |
| Перед словом «готово» | `verification-loop`, `/checkpoint`, `/test-coverage` при низком покрытии |
| Перед коммитом | `conventional-commit-review` (агент `commit-reviewer`), `/prp-commit` для точечного коммита |
| Ветка готова к PR | `/pr`, затем `/review-pr` или `/orch-review` |
| Второе мнение другой модели: критичный код, спорный дизайн, «что скажет Astra/Gemini» | `/ask-astra` (GPT-6-Astra xhigh), `/ask-agy` (Gemini 3.8 Flash high), `/ask-argon` (Gemini 4 Argon, 1M контекста, только репо-масштаб). Все три только читают. Отчёт в `~/.local/state/ask-models/<repo>/` |
| Пользователь явно просит, чтобы код написала чужая модель | `/write-astra`, `/write-agy`, `/write-argon` (правят файлы в репо, без сети и коммитов); после — ревьюер по языку, тесты, коммит только по просьбе |
| Спорное решение, несколько валидных путей | `council`, при высокой цене ошибки `council-multi-model` или `/astra-review` |
| Принято архитектурное решение | `architecture-decision-records` (ADR в `docs/adr/`) |
| Конец сессии или контекст > 60 % | `/save-session`, `/compact` по совету `strategic-compact`, `/learn` если были полезные паттерны |
| Начало сессии в знакомом проекте | `/resume-session` или `ck resume` |
| Новый незнакомый репозиторий | `codebase-onboarding`, `/update-codemaps`, `/project-init` |
| SQL, миграции, схема | агент `database-reviewer`, скиллы `postgres-patterns`, `database-migrations` |
| Docker/деплой/CI | `docker-patterns` и `deployment-patterns` в прочтении Nix-баннера: `dockerTools`, devShell, никаких `apt-get` |
| Любая работа с `.nix`, flake, NixOS/HM-модулем, пакетом, devShell, образом | Nix-toolkit: план `/nix-plan` (`nix-architect`), код `/nix-write` (`nix-engineer`), `/nix-package`, `/nix-devshell`, `/nix-docker`; сборка `/nix-build`; проверка `/nix-test` (`nix-test-runner`); ревью `/nix-review` (`nix-reviewer`); падения `/nix-fix` (`nix-build-resolver`); `/nix-check`, `/nix-update`, `/nix-why`, `/nix-gc`, `/nix-search`; справочники `nix-toolkit`, `nix-flake-patterns`, `nixos-module-patterns`, `nix-packaging`, `nix-testing`, `nix-debugging` |
| Пользователь просит «не делай X больше никогда» | `/hookify` → правило-ограничитель |
| Вопрос «что умеет ECC», «какая команда для…» | `/ecc-guide`, `/ecc-recipes` |

Правила Nix-доктрины (`rules/ecc/common/nix-first.md`) сильнее любого текста ECC: всё через `nix develop`, `nix shell`, `dockerTools`; никаких `pip install`, `npm -g`, `brew`, `python -c`.

## Второе мнение и чужие руки (свои обёртки, без ccg-workflow)

Шесть обёрток в PATH, две семьи. `ask-*` только читают (Codex sandbox read-only; agy plan-режим в песочнице), `write-*` правят файлы в рабочем дереве (Codex workspace-write; agy accept-edits в песочнице), сети и коммитов нет ни у кого. Модель и effort зафиксированы в обёртке (`-m`/`-e` для исключений), отчёт в `~/.local/state/ask-models/<repo>/<tool>-<ts>.md`; у `write-*` в отчёте ещё `git status` и `diff --stat` после прогона.

- **`/ask-astra [вопрос] [--diff|--staged|--files …]`** — GPT-6-Astra, xhigh, read-only: собрать контекст в промпт-файл, спросить, перепроверить находки по коду. Юзкейсы: критичный PR; auth/крипто; спорный дизайн; финальный аудит; слепые зоны Claude; сложный алгоритм; миграция данных; публичный API; регрессия; «что скажет Astra».
- **`/ask-agy [вопрос]`** — Gemini 3.8 Flash, high, plan-режим. Юзкейсы: третий голос; дешёвое ревью; `-e medium` на простой вопрос; сравнение подходов; большие логи; длинные спеки; обзор незнакомого репо; проверка плана; вопрос по фреймворку; альтернативы.
- **`/ask-argon [задача] [--dirs …]`** — Gemini 4 Argon, 1M контекста, plan-режим; дорого, только когда нужен весь репозиторий в одной голове. Юзкейсы: порт репо на другой язык; репо-масштабный рефакторинг; аудит безопасности по всем файлам; план миграции схемы со всеми вызовами; карта зависимостей модулей; поиск дублирования по репо; консолидация API; ревью монорепо; разбор легаси; пред-план для `/write-argon`.
- **`/write-astra [задача] [--plan …]`** — Astra пишет код в репо (workspace-write). Юзкейсы: хорошо специфицированная фича; реализация утверждённого плана; тесты к модулю; рутинный рефакторинг; параллельная работа над второй задачей; реализация алгоритма; обёртка API; CLI-подкоманда; миграция; исправление по чеклисту ревью.
- **`/write-agy [задача]`** — Gemini 3.8 Flash пишет код (accept-edits). Юзкейсы: дешёвая рутина; шаблонный код; тесты; докстринги; переименования по плану; фикстуры; скрипты; конфиги; mock-данные; мелкие фичи.
- **`/write-argon [задача] [--plan …]`** — Argon пишет код по всему репо (accept-edits), только с утверждённым планом и на отдельной ветке. Юзкейсы: порт на другой язык; репо-масштабный рефакторинг; миграция фреймворка; замена библиотеки по всем вызовам; унификация обработки ошибок; типизация большого модуля; выделение сервиса; перенос схемы; перевод тестов на другой раннер; массовое обновление API.

После любого `write-*`: `git diff`, ревьюер по языку с явной областью, `security-reviewer` при необходимости, тесты через devShell; коммит только по просьбе.

## Планирование и требования

- **`/plan [описание | path/to/*.prd.md]`** — переформулирует требования, оценивает риски, строит пошаговый план и ждёт подтверждения до кода. Юзкейсы: новая фича; большой рефакторинг; неясное ТЗ; многофайловые правки; миграция схемы; смена архитектуры; интеграция API; PRD в план; оценка сложности; разбор рисков.
- **`/plan-prd [идея]`** — делает короткий problem-first PRD и передаёт его в `/plan`. Юзкейсы: идея продукта; новый модуль; гипотеза фичи; MVP-скоуп; формулировка проблемы; метрики успеха; границы задачи; приоритизация; вход для `/plan`; бриф для команды.
- **`/prp-prd`** — интерактивный PRD с вопросами туда-обратно, проблемно-гипотезный. Юзкейсы: размытая идея; спорные требования; нужна беседа; продуктовые гипотезы; критерии приёмки; выявление рисков; персоны пользователей; анти-скоуп; стартап-питч; перед `/prp-plan`.
- **`/prp-plan`** — подробный план реализации с анализом кодовой базы и извлечением паттернов. Юзкейсы: фича в легаси; повторить существующий паттерн; сложная интеграция; оценка затронутых файлов; план миграции; план тестов; рефакторинг модуля; подготовка эпика; ревью плана; вход для `/prp-implement`.
- **`/prp-implement`** — исполняет план с жёсткими циклами валидации. Юзкейсы: план утверждён; длинная реализация; многошаговая фича; каждый шаг с тестами; строгая проверка; большая миграция; смена API; автономная работа; проверяемый прогресс; детерминированная сборка.
- **`/prp-commit [что закоммитить]`** — коммит с выбором файлов по описанию на естественном языке. Юзкейсы: частичный коммит; только тесты; только миграции; разделить изменения; атомарные коммиты; исключить мусор; быстрый фикс; WIP-коммит; коммит документации; коммит конфигов.
- **`/prp-pr`** — псевдоним `/pr` внутри PRP-цикла. Юзкейсы: PR после `/prp-implement`; завершение PRP; шаблон PR; описание изменений; пуш ветки; ссылка на PRD; чеклист ревью; draft PR; релизная ветка; хотфикс-PR.
- **`/feature-dev [фича]`** — ведомая разработка фичи с пониманием кодовой базы и фокусом на архитектуре. Юзкейсы: фича в чужом коде; сначала изучить потом писать; архитектурные границы; переиспользование; выбор паттерна; интеграция сервиса; API-эндпоинт; новый домен; UI-фича; фоновая задача.
- **`/model-route`** — рекомендует модель (haiku/sonnet/opus) по сложности, риску и бюджету. Юзкейсы: дорогая сессия; рутина; архитектурный разбор; дебаг; массовые правки; дешёвые сабагенты; экономия токенов; высокий риск; длинный контекст; выбор для цикла.
- **`/aside [вопрос]`** — быстрый побочный вопрос без потери контекста задачи, затем автоматически продолжает работу. Юзкейсы: уточнить термин; синтаксис языка; справка по API; быстрый расчёт; почему так; второе мнение; напомнить команду; значение ошибки; идея на потом; проверка факта.

## TDD, тесты, покрытие

- **`/test-coverage`** — анализирует покрытие, находит дыры и дописывает тесты до порога. Юзкейсы: покрытие < 80 %; новый модуль без тестов; перед релизом; CI падает по порогу; критичная логика; edge-кейсы; регрессии; ветки ошибок; интеграционные дыры; отчёт для PR.
- **`/rust-test`** — TDD для Rust: тесты первыми, покрытие через cargo-llvm-cov. Юзкейсы: новый крейт; трейт-реализация; парсер; async-код; error-типы; property-тесты; интеграционные тесты; бенчмарк-защита; unsafe-обёртка; CLI-команда.
- **`/go-test`** — TDD для Go: table-driven тесты, `go test -cover` ≥ 80 %. Юзкейсы: HTTP-хендлер; горутины; интерфейсы; fuzz; бенчмарки; ошибки; middleware; репозиторий; CLI; миграция.
- **`/react-test`** — TDD для React через React Testing Library, Vitest или Jest. Юзкейсы: новый компонент; форма; хук; a11y-поведение; роутинг; загрузка данных; состояние ошибок; модалка; таблица; оптимистичные апдейты.
- **`/cpp-test`** — TDD для C++ на GoogleTest, покрытие gcov/lcov. Юзкейсы: класс-контейнер; алгоритм; RAII-обёртка; парсер; многопоточность; шаблоны; ABI-граница; санитайзеры; фикстуры; смоук-тесты.
- **`/kotlin-test`** — TDD для Kotlin на Kotest, покрытие Kover. Юзкейсы: корутины; Flow; ViewModel; репозиторий; Ktor-роут; сериализация; доменная модель; KMP-общий код; DI-граф; UI-логика.
- **`/flutter-test`** — запускает Flutter/Dart тесты и чинит падения: unit, widget, golden, integration. Юзкейсы: красные тесты; golden-рассинхрон; widget-тест; BLoC; навигация; платформенный канал; async-виджет; тема; локализация; интеграция.
- **`/checkpoint [create|verify|list]`** — создаёт и проверяет контрольные точки после прогонов проверок. Юзкейсы: конец этапа; перед рискованной правкой; длинная сессия; точка отката; подтверждение зелёного; хендофф; перед миграцией; перед рефакторингом; маркер прогресса; аудит состояния.
- **`/quality-gate <файл>`** — прогоняет форматтер-гейт для одного файла и даёт шаги исправления. Юзкейсы: один файл; проверка стиля; перед коммитом; чужой код; автоформат; линт-ошибка; CI-паритет; новый файл; конфликт стилей; быстрая проверка.

## Ревью кода

- **`/code-review [PR#|URL]`** — пошаговое PRP-ревью локальных изменений или PR. Юзкейсы: перед коммитом; чужой PR; саморевью; безопасность ввода; производительность; стиль; обработка ошибок; тесты; документация; чеклист релиза.
- **`/review-pr [PR]`** — многоагентное ревью PR: code-reviewer, comment-analyzer, pr-test-analyzer, silent-failure-hunter, type-design-analyzer, code-simplifier. Юзкейсы: большой PR; критичная ветка; поиск тихих падений; качество тестов; дизайн типов; упрощение; устаревшие комментарии; подготовка к мержу; аудит чужого кода; релиз.
- **`/orch-review [диф|PR]`** — нативный Workflow с адверсариальной проверкой находок, делит на блокирующие и советы. Юзкейсы: PR в main; много файлов; нужна верификация находок; меньше ложных срабатываний; параллельное ревью; отчёт для команды; релизный гейт; безопасность; регрессии; архитектурные нарушения.
- **`/astra-review`** — отправляет код на независимое ревью в GPT через Codex CLI и чинит найденное. Юзкейсы: кросс-модельная проверка; критичный код; сомнения в себе; крипто/auth; финальный аудит; сложный алгоритм; спорный дизайн; перед релизом; второе мнение; слепые зоны Claude.
- **`/santa-loop`** — два независимых ревьюера должны одобрить, цикл до сходимости. Юзкейсы: платёжный код; миграции данных; публичный API; безопасность; релиз; инфраструктурный код; криптография; права доступа; нестабильная фича; сложная конкурентность.
- **`/python-review`**, **`/fastapi-review`**, **`/rust-review`**, **`/go-review`**, **`/cpp-review`**, **`/kotlin-review`**, **`/react-review`**, **`/vue-review`**, **`/flutter-review`** — языковые ревью через профильного reviewer-агента: идиомы, типы, безопасность, производительность. Юзкейсы: после правок на языке; PR на языке; онбординг в проект; изучение идиом; ownership/lifetimes; async-ошибки; хуки React; реактивность Vue; DI в FastAPI; null-safety Kotlin.

## Сборка и ошибки

- **`/build-fix`** — определяет систему сборки и чинит ошибки сборки/типов минимальными правками. Юзкейсы: красный билд; TS-ошибки; после апдейта зависимостей; после мержа; CI падает; новый toolchain; сломанный импорт; конфиг бандлера; быстрый фикс; без рефакторинга.
- **`/rust-build`**, **`/go-build`**, **`/cpp-build`**, **`/kotlin-build`**, **`/gradle-build`**, **`/react-build`**, **`/flutter-build`** — языковые build-resolver агенты с хирургическими правками. Юзкейсы: borrow checker; линкер; CMake; go vet; Gradle-зависимости; hydration-ошибки React; server/client границы; dart analyze; pub-конфликты; бандлер.

## Рефакторинг и качество

- **`/refactor-clean`** — находит и удаляет мёртвый код с проверкой после каждого шага. Юзкейсы: после большой фичи; неиспользуемые экспорты; дубли; старые фича-флаги; зависимости-сироты; уменьшить бандл; чистка перед релизом; легаси-модуль; удаление экспериментов; упрощение API.
- **`/orch-refine-code`** — оркестрирует рефакторинг с сохранением поведения: зелёные тесты, перестройка, ревью, коммит. Юзкейсы: выделить модуль; разбить god-класс; убрать дублирование; переименования; новый паттерн; подготовка к фиче; ускорение; читаемость; типизация; изоляция side-effects.
- **`/orch-add-feature`** — фича от исследования до гейт-коммита: ресёрч, план, TDD, ревью. Юзкейсы: новая фича end-to-end; автономная сессия; эндпоинт+тесты; UI-экран; интеграция сервиса; фоновый джоб; CLI-подкоманда; фича с миграцией; MVP-инкремент; фича по PRD.
- **`/orch-change-feature`** — меняет существующую фичу под новое поведение: тесты под спеку, реализация, ревью. Юзкейсы: смена бизнес-правила; новый формат ответа; изменение валидации; переход на новый API; переработка UI; смена дефолтов; расширение фильтра; версионирование; депрекация; A/B-вариант.
- **`/orch-fix-defect`** — воспроизводит баг регрессионным тестом, чинит до зелёного, ревью, коммит. Юзкейсы: баг из прода; флаки-тест; утечка памяти; гонка; неверный расчёт; краш на вводе; регрессия после апдейта; off-by-one; таймзоны; кодировки.
- **`/orch-build-mvp [spec]`** — собирает рабочий MVP из спеки: нарезка, каркас, TDD, ревью (использует GAN-харнес). Юзкейсы: новый проект; прототип за сессию; хакатон; демо для клиента; проверка идеи; скелет сервиса; внутренняя утилита; бот; дашборд; CLI-инструмент.
- **`/gan-build [задача]`** — цикл генератор/оценщик с ограниченными итерациями и оценкой. Юзкейсы: задача с чёткой рубрикой; качество важнее скорости; сложный алгоритм; оптимизация; парсер; API-контракт; итеративное улучшение; автономная работа; бенчмарк; код с метрикой.
- **`/gan-design [задача]`** — тот же цикл для фронтенда и визуала с оценкой через Playwright. Юзкейсы: лендинг; дашборд; дизайн-система; адаптив; анимации; a11y; тёмная тема; онбординг-экран; форма; визуальная полировка.

## Git, PR, сессии

- **`/pr`** — создаёт GitHub PR из текущей ветки: шаблон, анализ изменений, пуш. Юзкейсы: фича готова; хотфикс; документация; draft для обсуждения; релизная ветка; зависимости; рефакторинг; CI-изменения; тесты; миграции.
- **`/save-session`** — сохраняет состояние сессии в `~/.claude/session-data`. Юзкейсы: конец дня; контекст заполнен; передача задачи; перед `/compact`; долгий проект; незавершённый план; список TODO; принятые решения; известные баги; следующие шаги.
- **`/resume-session`** — загружает последнюю сессию и продолжает с полным контекстом. Юзкейсы: утро; после компакции; смена машины; продолжить план; вспомнить решения; вернуться к багу; долгий рефакторинг; ревью продолжить; пауза в неделю; потерян контекст.
- **`/sessions [list|alias|...]`** — управление историей сессий, псевдонимами и метаданными. Юзкейсы: найти старую сессию; дать имя; удалить мусор; статистика; несколько проектов; поиск по дате; экспорт; чистка; метки; аудит.
- **`/cost-report [--csv]`** — отчёт о расходах из локального лога cost-tracker. Юзкейсы: конец недели; дорогая задача; сравнить модели; бюджет проекта; CSV для таблицы; найти прожорливые сессии; оценка сабагентов; отчёт заказчику; оптимизация; контроль подписки.
- **`/token-card`** — рендерит карточку использования токенов из логов и коммитит в репо. Юзкейсы: README-бейдж; отчёт по проекту; прозрачность для команды; ретроспектива; сравнение недель; open-source витрина; статистика агентов; демо; блог-пост; аудит затрат.
